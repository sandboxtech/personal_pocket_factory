# 戴森环计划 — 设计文档

日期：2026-07-31
状态：待实现
基线：现有 `personal_pocket_factory` 场景（口袋世界 v1，1091 行 Lua）

---

## 一、这一版改了什么

v1 的玩法是"口袋世界加工 + 公共世界采集 + 体力兑经验"，经验是个没有用途的数字。
这一版给经验找到了唯一的兑现方式，并顺带重构了个人世界的形状和玩家之间的连接方式。

三条新玩法：

1. **关联箱物流**：玩家造的木箱在公共世界放下时自动变成关联箱，`link_id = player.index`。
   五个星球上铺出去的所有投递口，全部通向自己戴森环正中央那**一组 12 个**固定收货箱
   —— 同一个库存，12 个并行存取口。
2. **戴森环**：个人世界从 256×256 的方块，变成一条高 96、宽度随等级增长的环带。
   宽度是经验的唯一兑现方式。
3. **12 种经验**：科技瓶按种类分别记账，各自取 `log10` 求和决定环的宽度。
   缺任何一种，那一项就是 0 —— 逼玩家跑遍五个星球。

外加两条新压力：

- **科技会漏水**：公共世界重置时，全服每个已研究的有限科技以 `k × 瓶子种数 %` 的概率被撤销。
  科技树越深漏得越快，全服水位由集体产能决定。
- **弃厂会公有化**：离线 30 小时后戴森环变公共，任人进出拆改，产出汇进全服公共库存；
  50 小时后删除表面。**经验和环宽一点不丢**，回来重新长出来。

## 二、戴森环（个人世界）

### 2.1 几何

```
map_gen_settings = { width = 0, height = 96 }
```

`height = 96` 是**引擎级硬边界**，`|y| ≥ 48` 的区块根本不生成，零成本零代码。
`width = 0`（无限）交给脚本用 `on_chunk_generated` 手工涂砖控制。

| 区域 | 砖 | 说明 |
| --- | --- | --- |
| `y ∈ [-16, 16)`，`|x| < 半宽` | `concrete` | 唯一能站能建的 32 格 |
| `y ∈ [-48,-16) ∪ [16, 48)`，`|x| < 半宽` | `empty-space` | 上下各 32 格，纯视觉，不可通行 |
| `|x| ≥ 半宽` | `out-of-map` | 涂出来的墙，玩家走不过去 |
| `|y| ≥ 48` | — | 引擎不生成，代码里不出现 |

**为什么高度取 96 而不是 128**：两者触及的区块行数一样多（都跨在 `y = ±32` 的区块线上），
但 96 让引擎边界和环带边界重合，涂砖器就**只需要写 concrete 和 empty-space 两种砖，永远不涂 void**。

**为什么放弃 v1 的"宽高都用引擎硬边界"**：`PROJECT.md` 第三条约束原本论证的是"不需要自己铺虚空、
也不需要事后 `delete_chunk`"。但硬边界有两个致命限制：**只能是矩形**，而且**在已存在的 surface 上能不能改大是未验证的**。
戴森环这种"中间实心、上下临空、两侧延伸"的形状硬边界做不出来，无缝扩容也做不到。
这条约束的理由需要在 `PROJECT.md` 里重写。

### 2.2 宽度公式

```
戴森环等级 L = floor( Σᵢ max(0, log10(expᵢ)) )     i 遍历 12 种科技瓶
半宽      = 16 × (2 + L)      单位 tile
x 的有效范围 = [-半宽, 半宽)
```

新人 `L = 0`，`x ∈ [-32, 32)`，即 64×96 的起步环带（可用混凝土 64×32 = 2048 tile）。
每升一级，**两侧各外推 16 tile**，总宽 +32 tile（一个区块）。

手工涂砖之后区块对齐不再有意义（`set_tiles` 是逐 tile 的），所以每级两侧各 16 tile 即可，不用凑整区块。

**为什么用 log10**：等价于"经验每翻 10 倍，世界才多长一格"。大佬的经验是新人的 1000 倍，
环却只宽 3 格。这从根上解决了公开服"新人永远追不上"的问题，且不需要任何人为封顶或衰减规则。

**为什么每种单独取 log10 再求和**：`Σ log10(expᵢ) = log10(∏ expᵢ)`。
因为 `log10(1) = 0`，**任何一种瓶子没攒过，那一项就是 0**。这是 12 种分开记账的全部理由 ——
它逼玩家集齐，而不是把红瓶刷到天上。

不设上限。12 种各刷到 100 万经验时 `L = 72`，半宽 1184，总面积约 2368×96，
按区块算不到 250 个，对存档完全无压力。

增长曲线：

| 进度 | Σlog10 | L | 总宽 |
| --- | --- | --- | --- |
| 新人 | 0 | 0 | 64 |
| 红瓶 ×10 | 1 | 1 | 96 |
| 红瓶 ×1000 | 3 | 3 | 160 |
| 12 种各 ×10 | 12 | 12 | 448 |
| 12 种各 ×1000 | 36 | 36 | 1216 |
| 12 种各 ×100 万 | 72 | 72 | 2368 |

### 2.3 涂砖与扩容

**`on_chunk_generated`**：判断该 surface 是否戴森环；是则按 2.1 的表逐 tile 算砖并 `set_tiles`。
只有 `y ∈ [-48, 48)` 的区块会触发（引擎保证），所以每个区块最多处理 32×96 个 tile 中的一部分。

**升级时**：`exp.add` 后重算 `L`。若 `L` 增加，取旧半宽到新半宽之间的两条竖带（各 16×L增量 宽、96 高），
`request_to_generate_chunks` + `force_generate_chunk_requests` 保证区块存在，再 `set_tiles` 把
`out-of-map` 改写成 `empty-space` / `concrete`。一次升级最多重涂 32×96 = 3072 个 tile，开销可忽略。

**环外溢出**：玩家站在环的边缘时，引擎会顺手预生成边界外的两三个区块。这些区块的 tile 全部涂
`out-of-map`，**区块本身保留不删**。溢出量级是每人几个区块，可接受。
（对比：若不涂墙、任由玩家走出去，无限地图的生成量没有上限。）

### 2.4 收货箱阵列

戴森环正中央有 **12 个**脚本放置的 `linked-chest`，排成**两列 × 六行**，以原点双向对称：

```
tile x ∈ {-1, 0}          实体中心 x = ±0.5
tile y ∈ {-3,-2,-1,0,1,2} 实体中心 y = -2.5 … 2.5
```

整块占 2×6 tile，完全落在 `y ∈ [-16, 16)` 的混凝土带里，两侧各留 15 格给产线。

每个箱子：

- `link_id = player.index`（12 个**全部相同**）
- `destructible = false`、`minable = false` —— 不可摧毁、不可挖走
- `operable = true` —— 必须能打开，否则取不到货
- 坐标**永不随扩容移动**。环向两侧对称生长，箱阵始终在正中央，是玩家永远认得的地标。

**为什么是 12 个而不是 1 个**：12 个同 `link_id` 的箱子共享的是**同一个库存**，
所以这不是 12 倍容量，是 **12 个并行存取口**。12 个机械臂可以同时从同一批货里抓取，
而单个箱子只能被有限几个机械臂围住。**用箱子数量换吞吐量，而不是换容量**。
（数字 12 和 12 种科技瓶无关，纯粹是吞吐量考虑。）

创建时机：`pockets.ensure()` 里，和 surface 一起。已存在则跳过（幂等）。

### 2.5 离线生命周期：30 小时变公共，50 小时删除

替换 v1 的 `pocket_keep_offline_minutes = 30`（30 **分钟**就删）。新规则分两段：

| 离线时长 | 状态 | 行为 |
| --- | --- | --- |
| < 30 小时 | `private` | 正常。只有主人能进 |
| 30–50 小时 | `public` | 12 个箱子 `link_id` 改成**公共 id**；任何玩家可以进入，**完全自由：能拆能改能搬空** |
| > 50 小时 | 删除 | 撤走里面的人 → `delete_surface`。**经验保留** |

**回归**：主人在 30–50 小时之间上线，12 个箱子 `link_id` 立即恢复成 `player.index`，
状态回 `private`，当时在里面的其他玩家被撤回各自的戴森环。

**回归时公共库存里的货留在公共库存，主人拿不走。** 切回个人 `link_id` 后，
箱子显示的是他自己那份旧库存。公共期间的产出归公共 —— 规则干净，也是离线 30 小时的实际代价。

**50 小时后回来**：`pockets.ensure()` 重新生成 surface。经验没丢，所以环的宽度**立刻恢复到离线前的样子**，
箱阵重建，`link_id` 是他自己的。丢的是环上的建筑。

#### 公共 id

```
PUBLIC_LINK_ID = 0        -- player.index 从 1 开始，永不碰撞
```

**全服只有一个公共库存**。所有弃厂的产出汇进同一个池子，谁跑到任何一个公共环都能取。
这有聚集效应：公共环越多，那个池子越有价值，玩家越有理由去逛别人的废墟。

#### 为什么这样设计

这把"回收"从一个二元开关变成了**有中间态的过程，而中间态本身是玩法**——
弃厂不是消失，是先变成公共资产：它继续运转、产出汇进全服公共池，任人拆解取用。

同时它修掉了 v1 一个很粗暴的设定：离线半小时回来工厂就没了。现在是 30 小时才开始有后果，
50 小时才真的删，而且删的只是建筑，进度（经验、环宽）一点不丢。

#### 实现要点

- 状态存 `storage.ring_state[玩家名]`，取值 `'private'` / `'public'`。这是**状态机的真相源**，
  不要每次从 `last_online` 现算 —— 需要检测**状态跃迁**才能决定要不要改 `link_id`。
- 周期任务（沿用 `tick.lua` 的互质模数门控）扫描离线玩家，做 `private → public` 和 `public → 删除` 两个跃迁。
- `public → private` 在 `on_player_joined_game` 里做，立即生效，不等周期任务。
- 改 `link_id` 时遍历 `surface.find_entities_filtered{name = 'linked-chest'}` 全改
  —— 不要存箱子的 `LuaEntity` 引用，surface 重建后引用会失效。
- 删除前必须撤人（复用 `worlds.lua` 的 `evacuate` 思路），避免把人删进虚空。
- 阈值放 `storage.ring_public_hours`（30）/ `storage.ring_delete_hours`（50），可热调。

#### 存档体积的影响

保留时长从 30 分钟涨到 50 小时，surface 数量会明显上升。但戴森环很小：
典型玩家的环是 20–50 个区块，满级也才 250 个。100 个玩家各 50 个区块 = 5000 个区块，
和**一个**公共世界（64×64 = 4096 区块）同量级。可以接受。

真正的闸门变成了 50 小时那道删除，以及环带本身"高度被引擎钉死在 96"的形状约束。

#### 其他玩家怎么进入公共环

传送窗口里列出当前所有 `public` 状态的戴森环（显示原主人名字 + 环宽 + 已公共多久），
点击即传送。没有公共环时该区块隐藏。

### 2.6 出生与重生

出生点在收货箱旁边，`find_non_colliding_position('character', {4, 0}, 32, 1)`。
死亡一律重生回戴森环（沿用 v1 的 `on_player_respawned` 行为）。

### 2.7 关闭污染

创建 surface 后立即：

```lua
surface.override_pollution_type = {}   -- 注意：不是 nil
```

`Pollutant` 是个 table 概念 `{ pollutant = LuaAirbornePollutantPrototype? }`，
文档写明 **"If nil, pollution is disabled"**。而 `override_pollution_type` 本身也接受 nil，
含义是"不覆盖、跟随星球默认"。因为 Lua 里 `{pollutant = nil}` 求值就是空表 `{}`，
两种写法长得几乎一样、含义完全相反，且写错不会报错：

| 写法 | 含义 |
| --- | --- |
| `override_pollution_type = nil` | **不覆盖**，跟随默认 —— 污染照旧，静默 no-op |
| `override_pollution_type = {}` | 覆盖成"无 pollutant" —— **污染关闭** |

**为什么值得做**：戴森环开了 `no_enemies_mode`，污染本来就没有任何玩法效果（没虫子可招）。
但**污染扩散是 per-surface 每 tick 计算的**，而戴森环是每个玩家一份 surface。
人一多，一堆永远不会有虫子来的污染云在后台白烧 UPS。这是实打实的性能收益，不只是清掉地图上的红云。

公共世界**不动** —— 那是真星球，Nauvis 的虫子和 Gleba 的孢子都要靠污染驱动。
（这也是为什么不能用全局的 `game.map_settings.pollution.enabled = false`：它会一起把公共世界的污染关掉。）

**降级方案**：若 `{}` 的行为和预期不符，改为在 `tick.lua` 的周期调度里定期
`surface.clear_pollution()`。效果稍差（污染仍在算、只是被周期性抹掉），但一定有效。

## 三、关联箱

### 3.1 规则

| 场景 | 行为 |
| --- | --- |
| 玩家手搓木箱 | 产出替换成 `linked-chest` 物品（等量） |
| 在**公共世界**放下 `linked-chest` | `link_id = player.index`，可摧毁、可挖走 |
| 在**公共世界**放下 `wooden-chest` | 就地替换成 `linked-chest` 并绑 ID（兜底组装机产物和蓝图） |
| 在**戴森环**放下 `linked-chest` | 就地退化回 `wooden-chest`（家里要有普通储物箱可用） |
| 任何人试图改 `link_id` | 权限组拦截 |

只有**木箱**参与转化，铁箱/钢箱/物流箱不变。木箱 2 木头，是最便宜的容器，
专职化成"一次性外派投递口"很自然，也不需要额外的成本平衡。

**箱阵豁免**：戴森环里那 12 个预置关联箱是脚本 `create_entity` 出来的，
不触发 `on_built_entity`，所以不会被"退化回木箱"的规则误伤。
但若将来接了 `script_raised_built`，必须显式跳过它们 —— 判据是
`entity.destructible == false`（玩家放的箱子永远是可摧毁的）。

### 3.2 为什么这样设计

关联箱最初的风险是它等于"随身仓库"，会架空"必须背回家"的核心约束。
把**收货端限制成戴森环里唯一那个固定箱子**、并禁止玩家在戴森环内放置关联箱之后，
关联箱的语义变成了：**你在五个星球上铺出去的一堆投递口，全部通向家里那一个箱子**。

于是背包容量不再是瓶颈，但出门的意义反而更强了 —— 张力从"搬运"转移到"暴露在重置风险里的时间"：
星球重置时投递口全没了，家里的货还在，所以你要赶在重置前把投递口铺到矿脉旁边并尽量多送。

同一件物品的语义由所在星球决定（在家是储物，出门是投递口），玩家不需要管理两种箱子，
也不会出现"我把珍贵的关联箱浪费在家里了"的懊恼。

### 3.3 实现要点

- 事件：`on_player_crafted_item`（手搓替换）、`on_built_entity` / `on_robot_built_entity`（放置时判定）。
- 机器人建造时用 `entity.last_user.index` 取玩家；取不到则不绑定，保持普通木箱。
- 权限：`defines.input_action.set_linked_container_link_i_d`（已验证存在）加入 `players.lua` 的
  `BLOCKED_ACTIONS`，复用现有权限组机制。
- `LuaEntity.link_id` 是 `uint32` RW（已验证），`player.index` 也是 `uint32`，直接用。

### 3.4 关联库存的存续性（必须验证）

共享库存挂在 `link_id` 上而不是箱子上，所以理论上"一个箱子都不剩"时库存仍然存在。
但文档没有明确保证，而本设计有**两处**依赖这个假设：

1. 公共世界 `surface.clear()` 删掉那里的所有投递口 —— 但家里箱阵还在，有锚点兜底，风险低。
2. **离线 50 小时删除戴森环 surface 之后，该玩家的 `link_id` 一个箱子都不剩** ——
   如果引擎按引用计数回收库存，他攒的全部货物会在这一刻蒸发。

第 2 条是本设计最大的数据丢失风险，且**恰好打在离线最久、最不会来反馈的那批玩家身上**。

**必须在动工前实测**：造一个关联箱 → 放货 → 删掉所有引用该 `link_id` 的箱子 →
重新造一个同 `link_id` 的箱子 → 看货还在不在。

**若库存不存续，降级方案**：删除 surface 前把 12 个箱子的库存内容读出来存进
`storage.ring_stash[玩家名]`，重建 surface 时倒回去。多一份序列化代码，但杜绝丢货。

## 四、12 种经验与兑换

### 4.1 12 种科技瓶

`automation` / `logistic` / `military` / `chemical` / `production` / `utility` / `space` /
`metallurgic` / `agricultural` / `electromagnetic` / `cryogenic` / `promethium`，
物品名统一是 `<前缀>-science-pack`。

代码里按 `prototypes.item[name]` 是否存在来过滤，名字写错或版本改名时**降级跳过而不是崩溃**。

### 4.2 兑换公式

```
expᵢ += 该种瓶子数量 × 品质系数
```

品质系数：普通 1 / 罕见 3 / 稀有 5 / 史诗 7 / 传说 9。
（替换 v1 的 `constants.quality_exp` 的 1/2/3/4/5。）

体力走**门票制**：固定扣 `storage.convert_cost`（默认 1）点体力，背包里 12 种瓶子一次全兑。
先扣体力再移除物品，扣不掉就整个中止（沿用 v1 `exp.convert` 的顺序）。

**`values.lua` 整个删除**，`storage.item_value` 一并退休。
理由：12 种经验各自独立取 log10、互不换算，跨瓶种的定价问题根本不存在 ——
普罗米修斯瓶只喂普罗米修斯那一项，它跟红瓶从不在同一个数里比大小。
那套递归展开配方求原矿当量的代码失去了全部存在理由。

### 4.3 存储与迁移

```
storage.exp[玩家名] = { automation = 0, logistic = 0, ... }   -- 12 个键
```

v1 里 `storage.exp[玩家名]` 是个 number。迁移规则：老值整个折算进 `automation` 一项。
在 `constants.ensure_defaults()` 里做，检测到 number 就转换，幂等。

`storage.exp_log[玩家名]` 保留，记录最近一次兑换的明细（改成按瓶种分列）。

## 五、科技丢失

每个公共世界重置时（`worlds.reset_world` 内），对 `game.forces.player.technologies` 全表判定。

### 5.1 概率公式

```
P(丢失) = k × n / 100          n = 该科技配方里【不同科技瓶的种数】
                               k = storage.tech_loss_k，默认 1
```

`n` 从 `technology.research_unit_ingredients` 里数**不重复的物品名**得到。
例：`automation`（只要红瓶）n=1 → 1%；一个要红绿黑蓝紫黄六种的后期科技 n=6 → 6%。

### 5.2 豁免

| 类别 | 判据 | 理由 |
| --- | --- | --- |
| **Trigger 科技** | `prototype.research_trigger ~= nil` | 永不丢失。它们不是"研究"出来的，是触发出来的，撤销后玩家没有合法途径重新拿到 |
| **无限科技** | `prototype.level < prototype.max_level` | 不参与。它们 `researched` 恒为 false、用 `level` 计数，改 `level` 会让规则难以解释 |
| **未研究的** | `researched == false` | 无从谈起 |

Trigger 科技天然没有 `research_unit_ingredients`，`n = 0`、概率本来就是 0 ——
但仍然**显式跳过**。"规则恰好算出正确答案"和"规则明确表达意图"是两回事，后者才经得起改动。

### 5.3 为什么用瓶子种数而不是固定概率

固定 5% 有个隐患：`automation` 和终局科技一样容易丢，玩家可能上线就发现造不出传送带。

挂到瓶子种数上之后，**科技树越深越容易漏水，地基反而最稳固**。
更重要的是它形成了一个**自然的高度上限而不需要任何人为封顶**：
科技树越往上，单位时间的侵蚀速率越高，全服最终会停在"集体产能刚好能补上漏水速度"的那个高度。
水位由玩家的产能决定，不是由某个写死的数字决定。

按五星球错峰、120 分钟周期（每 24 分钟判定一次）估算：
n=1 的科技半衰期约 27 小时，n=6 的约 4.6 小时。

### 5.4 其他

- 撤销后全服广播丢失清单
- 撤销科技**不会删除已放置的建筑**（引擎行为），但对应配方会锁住，玩家造不出新的。这是设计意图
- `math.random` 在 Factorio 里是确定性的、多人同步安全的，直接用

## 八、实现顺序与风险

### 第一步必须先做验证（在写任何玩法代码之前）

五件事只能在游戏里实测，都可能推翻方案。**按危险程度排序**：

1. **关联库存在"零个箱子引用"后是否存续**（详见 3.4）。这是唯一会**丢玩家数据**的一条。
   造箱 → 放货 → 删光所有同 `link_id` 的箱子 → 重建一个 → 看货在不在。
   **降级方案**：删 surface 前序列化进 `storage.ring_stash[玩家名]`，重建时倒回。
2. **`linked-chest` 物品是否可插入、可放置**。它是编辑器用的原型，可能带 `only-in-cursor` 之类的 flag。
   **降级方案**：不做手搓替换，改成只在放置木箱时用脚本 `create_entity` 造关联箱实体。
3. **`empty-space` 砖能不能设在普通 surface 上**。它是太空平台的背景砖，
   引擎可能限制它只能出现在 `platform` 类型的 surface。
   **降级方案**：改用 `out-of-map`（功能等价，只是看不到宇宙背景），或换一种深色装饰砖。
4. **`surface.override_pollution_type = {}` 是否真的关掉污染**（详见 2.7 的 Lua 陷阱）。
   验证方法：设完之后读 `surface.pollutant_type`，应为 nil。
   **降级方案**：周期 `surface.clear_pollution()`。
5. **`map_gen_settings = {width = 0, height = 96}` 的实际生成范围**，确认 `|y| ≥ 48` 真的不生成区块。

建议做法：起一个空场景，用 `/c` 手动跑这五段，确认后再动工。第 1 条不通过就必须先改设计。

### 已验证的 API（本次查证）

- `defines.input_action.set_linked_container_link_i_d` 存在 —— 权限组能锁死改 ID
- `LuaEntity.link_id` 是 `uint32` **RW**
- `LuaForce.technologies` 存在，`LuaTechnology.researched` **可写**
- `character_*` 加成在 `LuaEntity` 上**不存在**，在 `LuaForce` 上是全服共享，
  在 `LuaPlayer` 上是**每人独立且可写** —— 本版没用到，但记下来备查

### 一个不影响动工但你该知道的问题

12 种瓶子里，**太空瓶和普罗米修斯瓶可能实际上拿不到**。
它们需要发射火箭建太空平台，而火箭只能从**星球**发射 —— 戴森环是普通 surface，不是星球。
玩家只能在每 2 小时就重置的公共世界里造火箭。

而 `k × n%` 的规则**加重了这件事**：火箭相关科技的瓶子种数多，是漏水最快的那一档。
全服可能长期够不到发射所需的科技高度。

好消息是这道坎只有一次：**太空平台是独立 surface，星球重置不影响它**，射上去就一直在。

两个调节旋钮：`storage.world_reset_minutes`（默认 120，开服后大概率要调大）
和 `storage.tech_loss_k`（默认 1，觉得科技水位压不上去就调小）。

后果：现实中 `Σlog10` 大概会卡在 10 种瓶子上，环宽的理论上限拿不到。这不是 bug，
只是意味着「集齐 12 种」是一个**服务器级别的长期目标**而不是个人目标。
